\begin{abstract}
\setlength{\parindent}{2em}
本报告面向国产芯片上的大模型推理吞吐优化任务，在官方指定的 FlagOS 栈（vllm-plugin-FL 分支 flagos-2026-s2、FlagGems 标签 v5.3.5）上，对 MiniCPM5-2B 在天数 BI-V150 与沐曦曦云 C500 两款芯片开展有开发量的算子、内核与调度优化，全部工作均不修改 \texttt{vllm serve} 启动参数、不更换模型、不降低精度。

性能方面，沐曦 C500 平台 4k 场景总吞吐达到 11868.79–12403.21 tok/s，为官方基线的 2.33–2.44 倍；16k 场景达到 11098.02–11167.87 tok/s，为基线的 1.58–1.59 倍。天数 BI-V150 平台 4k 场景由官网基线 2028.01 提升至 2606.56 tok/s（+28.5\%），16k 场景由 915.15 提升至 3541.34 tok/s（+287\%）；其中 A20 自研内核在同日交错 A/B 下，相对当日 stock 再提升 16.4\% 与 19.8\%。精度方面，MATH-500 Level 3 保持在 96.2\%–98.1\%，高于 95\% 的赛题要求；TTFT 在各场景均未回退。

主要技术贡献包括：（1）面向国产芯片的 shape-aware 分派方法论；（2）免排序的 top-p 采样链，用 1024-bin 质量直方图替代全词表排序，保留集质量有下界保证；（3）自研 paged decode attention 内核，从 PV 矩阵乘的累加器布局转换这一具体瓶颈出发，使 decode attention 带宽由 258 GB/s 提升到 372 GB/s；（4）一套可复核的“微基准—当日交错 A/B—官方口径验收”测量闭环，并给出全部被否决方案的实证与原因；（5）算子族级的热路径构成剖析与四项硬约束的达标裕度矩阵，把“快了”与“没有偷工减料”放在同一组图里交代清楚。

\noindent\textbf{关键词：}国产芯片；推理吞吐；算子融合；paged decode attention；shape-aware dispatch；vLLM
\end{abstract}

\section{引言}
大语言模型规模化落地后，推理阶段的算力与显存开销成为主要成本项。在固定硬件、固定框架、固定模型的前提下提升端到端吞吐，需要在算子、内核与调度三个层面同时发力。本报告以 MiniCPM5-2B\cite{minicpm} 为对象，在国产 AI 芯片（天数 BI-V150 与沐曦曦云 C500）上，基于官方指定的 FlagOS 软件栈（vllm-plugin-FL\cite{vfl} 与 FlagGems\cite{fg}）开展有开发量的优化工作。

与通用 GPU 生态不同，国产芯片在指令集、访存层次、运行时与算子库上的差异，使得许多在 NVIDIA 上默认成立的配置（如 Triton 的 \texttt{num\_warps=4, num\_stages=3}）在这些平台上系统性失配。本报告的一个核心观察是：\textbf{先用微基准把瓶颈定位到具体的内核或同步点，再决定改配置、改内核还是改调度}；任何改动都必须通过官方 benchmark 的当日交错 A/B 与 MATH-500 精度复核，未通过者一律回退留档。

本文的主要贡献如下：
\begin{itemize}
  \item \textbf{双平台的端到端收益}：在官方 FlagOS 栈上完成 MiniCPM5-2B 的推理吞吐优化，沐曦 C500 的 4k 场景达到官方基线的 2.33–2.44 倍、16k 场景 1.58–1.59 倍；天数 BI-V150 的 4k 由 2028.01 提升至 2606.56 tok/s、16k 由 915.15 提升至 3541.34 tok/s，且精度与 TTFT 均满足赛题约束。
  \item \textbf{一套可复核的优化闭环}：提出并实践“微基准定位 $\rightarrow$ 最小改动验证 $\rightarrow$ 官方口径当日交错 A/B”的流程，并用它系统性地证伪了若干在隔离测量中看似有利、在端到端上却净亏的方案（W8 权重量化、n-gram 投机采样、IR 级 RMSNorm 融合、shape-aware 分派等），每一项都保留了可复现的否决证据。
  \item \textbf{两张卡的性能边界测量}：给出 decode attention 与 decode GEMM 在两种芯片上的带宽实测，指出 C500 的 paged decode 已达 1466 GB/s（超过标称带宽）、天数的自研内核 372 GB/s 对应该卡可达负载带宽的约 70\%，从而为后续工作划定了明确的天花板。
\end{itemize}

\subsection{任务定义}
本赛题要求在不改变模型、不降低精度的前提下，提升 MiniCPM5-2B 在两指定国产芯片上的推理总吞吐（total tokens/s）。优化必须落在框架与算子内部，且需具备实际开发量：KV Cache 与动态批处理、算子融合、内核重写、自研量化策略等均在允许范围内；直接 merge 上游分支、修改 benchmark 脚本、或在缺乏算子优化的情况下切换算子均被禁止。

代码与证据的对应关系也随之固定：算子本体在 FlagGems，框架接入在 vllm-plugin-FL，性能数据来自官方脚本，精度来自 evalscope 与探针。这样既能逐行审查实现，又能避免“报告写了策略、提交里却没有代码”的问题。

（1）Profile 定位：先用 serve 时序日志（PagedAttention 式分页 KV 管理见文献\cite{vllm}）、设备侧计时与 host 打点区分时间究竟花在 GPU 内核、host 发射还是隐式同步；（2）探针先行：任何替换或新内核，先在独立脚本里做全形状 bit-exact 或统计等价验证，再上 serve；（3）Shape-aware dispatch：同一算子保留多个等价实现或执行配置，按输入 shape 在派发层选择（赛题组 2026-10-10 已确认合规）；（4）官方口径验收：只用官方 benchmark 与 evalscope，serve 参数一字未改。

正确性按强度分三档：能 bit-exact 的（A6 双 gather、A7 发射配置）一律 bit-exact；只能统计等价的（采样融合、GEMM 路由）用分布对比加 MATH-500 复核；所有进入提交的改动都必须通过官方精度门槛，未通过的一律回退并留档，不进入提交代码。

\section{沐曦 C500：采样链、GEMM 路由与 host 同步消除}
\subsection{瓶颈画像}
初始 profile 显示，C500 的 decode 阶段存在三类互相独立的开销：采样尾部是纯 eager PyTorch（bf16$\rightarrow$fp32 cast、除温度、对 130560 词表排序取 top-p、gumbel-argmax），每步约 12 ms 且全在 host 串行；GEMM 存在布局与路由失配，vendor 高性能实现从 Python 侧不可达；prefill 每层还有隐式 DtoH 同步，造成 GPU 空闲。

这些话在算子层面才有说服力。图~\ref{fig:hotpath} 把同一基准（641 步）两次 profile 的 GPU 内核时间按算子族聚合（源：\path{docs/baselines/metax-c500/profile_baseline.txt} 与 \texttt{profile\_post\_opt1.txt}）：采样族占内核时间的 38.8\%（14.61 s），是最大的单项，其内部由全词表排序、全局直方图与 argmax 三个大 kernel 构成；融合后降到 5.1\%（1.24 s，净省 13.37 s）。与之对照，GEMM 与 attention 的绝对时间几乎不动（13.82$\rightarrow$13.81 s、7.19$\rightarrow$7.22 s），占比却分别升到 56.9\% 与 29.8\%——不是因为它们变慢了，而是总量被砍掉了三分之一。这张图同时解释了后续优化的顺序：opt2／opt8 去吃 GEMM，opt9／A20 去吃 attention，而不是继续在采样上打转。

\subsection{免排序的采样链（opt1／opt3／opt7／opt11）}

\subsection{GEMM 布局与路由（opt2／opt4／opt6／opt8／opt11）}
MACA Triton 的 \texttt{mm\_kernel} 只支持 nn 布局，且在 prefill 大 M 下比 vendor mcBLAS 慢 1.35–1.67 倍（126 组配置全扫仍不敌，vendor 约 197 TFLOPS 逼近峰值）；而 FlagGems 进程级接管 \texttt{aten::mm} 之后，vendor GEMM 从 Python 完全不可达。为此，prefill 大 M 改走 ctypes 直绑 libmcblas 的 \texttt{mcblasGemmEx}（cuBLAS 兼容 ABI），并注册为 custom op 保证 compiled 区域安全；decode 细瘦 M 保留自研 Triton nn\_db 单布局内核，权重只留一份，不额外占用显存。另修复 \texttt{vocab\_parallel\_embedding} 在 import 时绑死原版 \texttt{dispatch\_unquantized\_gemm} 导致 lm\_head 从未进入优化路由的问题，lm\_head 由 603 $\mu$s 降至 379 $\mu$s。

\subsection{自研 paged decode attention 内核（A20）}
在 A7 之后，decode attention 仍是整步中最大且唯一未压到带宽下限的一项。把 stock kernel 逐段拆开（同一 harness，B=64／kv=4096／16q-2kv／d=128／block=16／bf16）可见：loads+QK 已跑到 509 GB/s，softmax 几乎免费，而 PV 的 \texttt{tl.dot} 独占 0.36 ms——它必须把 p 从 MMA 累加器布局转换为 A 操作数布局，每个 KV block 都要过一次共享内存往返。瓶颈是布局搬运，不是带宽。

据此重写内核（算子位于 \texttt{FlagGems/fused/paged\_decode\_attention.py}，插件侧为薄封装与派发）：一个 CTA＝1 warp＝一个（seq, kv\_head, 段），使布局转换留在 warp 内；BLOCK\_N=16，p tile 不超过一个 MMA 形状；base-2 在线 softmax，scale 预折 $\log_2(e)$ 走 MUFU；主循环不加 mask，仅 ragged 尾部单独一个带 mask 的 block；段数固定、段长由 device 端 seq\_lens 现算（CUDA-graph 安全），段缓存 slab 在 \texttt{apply()} 即捕获前一次性预分配；段边界按整页对齐，进一步消去逐 token 除模与向量页 gather。混合步中的 decode 行也通过 \texttt{try\_fast\_decode} 进入同一内核。

\section{主要创新点}
（1）跨双平台的 shape-aware dispatch 统一框架。同一套“离线全空间扫描＋派发层按 shape 选择实现/配置”的方法论落在两种国产芯片上，覆盖 GEMM、attention、采样三类算子，且有赛题组明确的合规口径；本报告同时给出该框架的适用边界（见第~\ref{sec:negative}~节 A26）。

（2）免排序 top-p 采样。1024-bin 质量直方图 zoom 替代全词表排序，保留集质量恒不小于 $p\cdot Z$，是有下界保证的确定性构造而非近似猜阈值；双平台复用，采样链约 40 倍提速。

（3）发射数削减范式。dual-gather 利用 kv\_cache 页内 K/V 连续布局一次完成收集，配合 varlen out= 直写，把 prefill attention 的 host 开销从每请求 4 次发射降到 2 次，全部经 bit-exact 探针验证。

（4）配置维度的系统性诊断。指出 NVIDIA 默认启发式（w4s3）与 libtuner 在 event-timing 降级模式下于国产芯片上的失配根因，仅这一项即带来 4k/16k 各约 40\% 的端到端收益。

（5）自研 decode attention 内核。不是泛泛地“重写 flash attention”，而是先把 stock kernel 逐段拆开，定位到 PV 的 MMA 累加器布局转换这一具体瓶颈，再用单 warp、小 tile、base-2 softmax、尾部 mask 与页对齐分段逐项消除，使 decode attention 带宽由 258 GB/s 提升到 372 GB/s；并用“跳过 attention 的探针”量出该方向的硬件下限（19.3 ms/步）。

（6）零精度妥协与可复核闭环。所有性能改动要么 bit-exact，要么统计等价且通过 MATH-500 Level 3 实测；每个候选都有当日交错 A/B、原始 CSV、机器状态与回退开关，未通过 3\% 准入或精度门槛的一律不进入提交。

\subsection{复现注意事项}
（1）防止 prefix cache 污染：benchmark 使用 seed=0，同一 serve 上连跑两次相同 input\_len 的负载会产生完全相同的 prompt，第二次会大量命中 prefix cache（本队日志出现过 35.9\% 命中率），使 prefill 近乎免费、总吞吐虚高 30\% 以上。每个数据点都应在新启动的 serve 上获取，A/B 两侧均从冷缓存开始。

（2）C500 需要 $\geq$128 GB CPU 内存：在模力方舟 64 GB 内存规格实例上，纯镜像原版 \texttt{vllm serve} 也会在 inductor 编译阶段被 cgroup OOM killer 杀掉（匿名内存峰值 63.4 GB，被杀时 GPU 显存仅 858 MiB，与显存、负载、代码改动均无关）。128 GB 规格实例全程稳定。

（3）首次启动耗时：C500 需执行 GEMM autotune 预热，实测两台实例分别为 367 秒与 973 秒；第二次启动（triton cache 已存在）约 1–3 分钟。此为正常现象，不是卡死；如确需跳过可设 \texttt{VLLM\_FL\_MM\_WARMUP=0}，但 4k 吞吐约 −6\%、TTFT 变差。

（4）实例间差异：两台 C500 实例的 4k 吞吐相差 4\%、TTFT 相差 66\%，16k 几乎一致。报告因此以区间给数，不以单台最优值充当普遍成绩。

\section{结论与建议}
\subsection{结论}
本报告在官方指定的 FlagOS 栈上，完成了 MiniCPM5-2B 在天数 BI-V150 与沐曦曦云 C500 两款国产芯片上的推理吞吐优化。在不修改 \texttt{vllm serve} 参数、不更换模型、不降低精度的约束下，C500 平台 4k 场景达到官方基线的 2.33–2.44 倍、16k 场景 1.58–1.59 倍；天数平台 4k 由 2028.01 提升至 2606.56 tok/s（+28.5\%）、16k 由 915.15 提升至 3541.34 tok/s（+287\%）；MATH-500 Level 3 精度保持在 96.2\%–98.1\%，高于 95\% 的门槛，TTFT 在各场景均未回退。

从方法论上看，本工作验证了一条可复用的路径：先用微基准把时间归因到具体内核或同步点，再用最小改动验证，最后以官方口径做当日交错 A/B。这条路径既解释了为什么某些看似有利的方案（W8 量化、投机采样）在端到端上不可行，也解释了为什么某些微小改动（发射配置、双 gather）能带来数十个百分点的收益。

\subsection{局限与后续工作}
其一，本文的绝对值受开发实例状态影响较大，跨日不可比，因此天数侧一律以同日交错 A/B 的相对收益表述；其二，C500 侧在两台实例上的 4k 吞吐存在约 4\% 的差异，报告因此给区间而非单点；其三，decode attention 在内核层面已接近该卡的访存上限（C500 实测 1466 GB/s，天数 decode kernel 372 GB/s 对应其可达负载带宽的约 70\%），进一步提效需要脱离 Triton 或引入更低比特的 KV 表示，而后者在本文的实验中已因 gather 吞吐退化被否决。

后续工作可从三个方向展开：一是把 shape-aware 分派扩展到 prefill 侧的分块策略；二是探索编译器层面的算子融合（本文的 IR 级 RMSNorm 尝试因 inductor 失去相邻融合而失败，但换一种插入位置可能成立）；三是在更多国产芯片上复现同一套测量闭环，检验其可迁移性。

另外，当前上游有两项参考实现已按独立实验分支完成验证：\href{https://github.com/flagos-ai/vllm-plugin-FL/commit/71f6148}{common attention metadata graph（\#442）}与\href{https://github.com/flagos-ai/vllm-plugin-FL/commit/6182281}{图捕获前 prewarm CachedOps（\#552）}。前者修复 MetaX 指针类型后通过图测试，但官方 4k 负收益；后者通过 5 个单测，但稳态和启动均无收益。因此本报告的性能数字不包含这两项工作，也不直接 merge 上游主分支；详细原始日志见 \path{docs/experiments/a28-cachedop-prewarm.md} 与 \path{docs/experiments/a29-common-attention-metadata.md}。
