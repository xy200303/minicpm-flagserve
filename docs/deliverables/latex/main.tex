\begin{abstract}
\noindent 本报告面向国产芯片上的大模型推理吞吐优化任务，在官方指定的 FlagOS 栈（vllm-plugin-FL 分支 flagos-2026-s2、FlagGems 标签 v5.3.5）上，对 MiniCPM5-2B 在天数 BI-V150 与沐曦曦云 C500 两款芯片开展有开发量的算子、内核与调度优化，全部工作均不修改 \texttt{vllm serve} 启动参数、不更换模型、不降低精度。

性能方面，沐曦 C500 平台 4k 场景总吞吐达到 11868.79–12403.21 tok/s，为官方基线的 2.33–2.44 倍；16k 场景达到 11098.02–11167.87 tok/s，为基线的 1.58–1.59 倍。天数 BI-V150 平台 4k 场景由官网基线 2028.01 提升至 2606.56 tok/s（+28.5\%），16k 场景由 915.15 提升至 3541.34 tok/s（+287\%）；其中 A20 自研内核在同日交错 A/B 下，相对当日 stock 再提升 16.4\% 与 19.8\%。精度方面，MATH-500 Level 3 保持在 96.2\%–98.1\%，高于 95\% 的赛题要求；TTFT 在各场景均未回退。

主要技术贡献包括：（1）面向国产芯片的 shape-aware 分派方法论；（2）免排序的 top-p 采样链，用 1024-bin 质量直方图替代全词表排序，保留集质量有下界保证；（3）自研 paged decode attention 内核，从 PV 矩阵乘的累加器布局转换这一具体瓶颈出发，使 decode attention 带宽由 258 GB/s 提升到 372 GB/s；（4）一套可复核的“微基准—当日交错 A/B—官方口径验收”测量闭环，并给出全部被否决方案的实证与原因。

\noindent\textbf{关键词：}国产芯片；推理吞吐；算子融合；paged decode attention；shape-aware dispatch；vLLM
\end{abstract}

\section{优化方法论}
两张芯片共用同一套闭环，每一步都保留可复核的工件（探针脚本、profile 数据、单测、官方 benchmark 原始 CSV）。

（1）Profile 定位：先用 serve 时序日志、设备侧计时与 host 打点区分时间究竟花在 GPU 内核、host 发射还是隐式同步；（2）探针先行：任何替换或新内核，先在独立脚本里做全形状 bit-exact 或统计等价验证，再上 serve；（3）Shape-aware dispatch：同一算子保留多个等价实现或执行配置，按输入 shape 在派发层选择（赛题组 2026-10-10 已确认合规）；（4）官方口径验收：只用官方 benchmark 与 evalscope，serve 参数一字未改。

正确性按强度分三档：能 bit-exact 的（A6 双 gather、A7 发射配置）一律 bit-exact；只能统计等价的（采样融合、GEMM 路由）用分布对比加 MATH-500 复核；所有进入提交的改动都必须通过官方精度门槛，未通过的一律回退并留档，不进入提交代码。

\section{沐曦 C500：采样链、GEMM 路由与 host 同步消除}
\subsection{瓶颈画像}
初始 profile 显示，C500 的 decode 阶段存在三类互相独立的开销：采样尾部是纯 eager PyTorch（bf16$\rightarrow$fp32 cast、除温度、对 130560 词表排序取 top-p、gumbel-argmax），每步约 12 ms 且全在 host 串行；GEMM 存在布局与路由失配，vendor 高性能实现从 Python 侧不可达；prefill 每层还有隐式 DtoH 同步，造成 GPU 空闲。

\subsection{免排序的采样链（opt1／opt3／opt7／opt11）}
自研 Triton 内核（\texttt{FlagGems/fused/sampler\_fused.py}、\texttt{top\_p\_sample.py}）做三件事：其一，直接以 bf16 读取 lm\_head 输出，把温度折叠进 Gumbel-Max（$\arg\max(x/T+g)$ 与 $\arg\max(x+T\cdot g)$ 等价，$T<10^{-5}$ 时退化为 $\arg\max$）；其二，top-p 用质量直方图 zoom，单轮 1024-bin 直方图定位阈值 $\tau$ 所在 bin 并取其下沿，保留集质量恒不小于 $p\cdot Z$，完全替代全词表排序；其三，词表维 split-parallel（32 splits $\times$ BLOCK 4096），使小 batch 也能打满芯片。采样全链由约 12.4 ms 降至 0.31 ms/步。

正确性方面，greedy 与 \texttt{torch.argmax} 完全一致；top-p 样本全部落在核集内（含直方图粒度 slack），与原实现的 TV 距离处于纯采样噪声区间。

\subsection{GEMM 布局与路由（opt2／opt4／opt6／opt8／opt11）}
MACA Triton 的 \texttt{mm\_kernel} 只支持 nn 布局，且在 prefill 大 M 下比 vendor mcBLAS 慢 1.35–1.67 倍（126 组配置全扫仍不敌，vendor 约 197 TFLOPS 逼近峰值）；而 FlagGems 进程级接管 \texttt{aten::mm} 之后，vendor GEMM 从 Python 完全不可达。为此，prefill 大 M 改走 ctypes 直绑 libmcblas 的 \texttt{mcblasGemmEx}（cuBLAS 兼容 ABI），并注册为 custom op 保证 compiled 区域安全；decode 细瘦 M 保留自研 Triton nn\_db 单布局内核，权重只留一份，不额外占用显存。另修复 \texttt{vocab\_parallel\_embedding} 在 import 时绑死原版 \texttt{dispatch\_unquantized\_gemm} 导致 lm\_head 从未进入优化路由的问题，lm\_head 由 603 $\mu$s 降至 379 $\mu$s。

\subsection{消除 prefill 每层 DtoH 同步（opt10）}
prefill trace 中 GPU 空闲 18.1\%，元凶之一是 vendor flash\_attn 每层每步执行 \texttt{prefill\_seq\_lens.tolist()}（DtoH 强同步，42 层各一次）。改为纯 GPU cumsum 并缓存到当步 \texttt{attn\_metadata}，42 层只算一次：4k 提升 10.9\%、16k 提升 9.9\%，16k TTFT 由 20.8 s 降至 18.0 s。

\section{天数 BI-V150：vendor 接入、发射配置与自研 decode 内核}
\subsection{prefill attention 接入 vendor ixAttnBkd（A1／A6）}
iluvatar 后端缺少 flash\_attn 包时，attention 落到 vLLM 通用 Triton 参考实现，16k prefill 每层每 2048-chunk 需 36.8 ms，占 GPU busy 91.8\%。接入 vendor ixAttnBkd 内核并确认其 causal 语义为 bottom-right（cmt=2）与 vLLM 的 chunk prefill 对齐后，内核级实测在所有 kv 长度上均快 12–20 倍。配套地，builder 一次性完成每步 decode/prefill 划分，避免每层两次 D2H；KV 用自研 Triton \texttt{\_dual\_gather\_kernel} 一次完成 K+V 分页收集（bit-exact，GPU 106$\rightarrow$62 $\mu$s、host 68$\rightarrow$37 $\mu$s），varlen 分支用 out= 直写消除 copy-out，每请求发射数由 4 降为 2。

\subsection{decode unified-attention 发射配置重构（A7）}
stock Triton 默认 \texttt{num\_warps=4, num\_stages=3} 是面向 NVIDIA 数据中心的甜点配置，在 BI-V150 上系统性失配：软件流水线在每个 warp 档上都是负收益，warps 越少越好。离线扫描 3D 主内核与 reduce\_segments 全链路后，仅对 3D flash-decoding 路径固定为 w1 s1（TILE=16／SEG=16 经扫描本已最优），输出与 stock bit-exact（max\_diff=0.0）。这一项同时说明，配置维度是独立于算法维度的优化空间。

\subsection{自研 paged decode attention 内核（A20）}
在 A7 之后，decode attention 仍是整步中最大且唯一未压到带宽下限的一项。把 stock kernel 逐段拆开（同一 harness，B=64／kv=4096／16q-2kv／d=128／block=16／bf16）可见：loads+QK 已跑到 509 GB/s，softmax 几乎免费，而 PV 的 \texttt{tl.dot} 独占 0.36 ms——它必须把 p 从 MMA 累加器布局转换为 A 操作数布局，每个 KV block 都要过一次共享内存往返。瓶颈是布局搬运，不是带宽。

据此重写内核（算子位于 \texttt{FlagGems/fused/paged\_decode\_attention.py}，插件侧为薄封装与派发）：一个 CTA＝1 warp＝一个（seq, kv\_head, 段），使布局转换留在 warp 内；BLOCK\_N=16，p tile 不超过一个 MMA 形状；base-2 在线 softmax，scale 预折 $\log_2(e)$ 走 MUFU；主循环不加 mask，仅 ragged 尾部单独一个带 mask 的 block；段数固定、段长由 device 端 seq\_lens 现算（CUDA-graph 安全），段缓存 slab 在 \texttt{apply()} 即捕获前一次性预分配；段边界按整页对齐，进一步消去逐 token 除模与向量页 gather。混合步中的 decode 行也通过 \texttt{try\_fast\_decode} 进入同一内核。

\subsection{可复现性与可审计性}
内核每个（seq, kv\_head, segment）只依赖自己的 q／KV 页与 seq\_lens，段长只由该序列长度决定，因此同一序列的输出与批组成无关。FlagGems 侧配有 \texttt{tests/test\_paged\_decode\_attention.py}：8 个精度用例对照 fp32 参考，外加一个批量不变性用例（单条／两条／半批／全批／逆序全批逐位相等，并重复同组成验证确定性），BI-V150 上 9 passed。混合步的 decode 切片每 4000 次调用输出一行 used/skipped 计数，16k 两次实测均为 used=44000、skipped=0，即 100\% 命中自研内核，不存在隐式退回 stock 的情况。

\section{主要创新点}
（1）跨双平台的 shape-aware dispatch 统一框架。同一套“离线全空间扫描＋派发层按 shape 选择实现/配置”的方法论落在两种国产芯片上，覆盖 GEMM、attention、采样三类算子，且有赛题组明确的合规口径；本报告同时给出该框架的适用边界（见第 7 节 A26）。

（2）免排序 top-p 采样。1024-bin 质量直方图 zoom 替代全词表排序，保留集质量恒不小于 $p\cdot Z$，是有下界保证的确定性构造而非近似猜阈值；双平台复用，采样链约 40 倍提速。

（3）发射数削减范式。dual-gather 利用 kv\_cache 页内 K/V 连续布局一次完成收集，配合 varlen out= 直写，把 prefill attention 的 host 开销从每请求 4 次发射降到 2 次，全部经 bit-exact 探针验证。

（4）配置维度的系统性诊断。指出 NVIDIA 默认启发式（w4s3）与 libtuner 在 event-timing 降级模式下于国产芯片上的失配根因，仅这一项即带来 4k/16k 各约 40\% 的端到端收益。

（5）自研 decode attention 内核。不是泛泛地“重写 flash attention”，而是先把 stock kernel 逐段拆开，定位到 PV 的 MMA 累加器布局转换这一具体瓶颈，再用单 warp、小 tile、base-2 softmax、尾部 mask 与页对齐分段逐项消除，使 decode attention 带宽由 258 GB/s 提升到 372 GB/s；并用“跳过 attention 的探针”量出该方向的硬件下限（19.3 ms/步）。

（6）零精度妥协与可复核闭环。所有性能改动要么 bit-exact，要么统计等价且通过 MATH-500 Level 3 实测；每个候选都有当日交错 A/B、原始 CSV、机器状态与回退开关，未通过 3\% 准入或精度门槛的一律不进入提交。

\subsection{复现步骤}
安装：在两个源码目录分别执行 \texttt{pip install -e . --no-build-isolation}。C500 还需 \texttt{export PATH=/opt/conda/bin:\$PATH}、\texttt{MACA\_PATH=/opt/maca}、\texttt{MACA\_HOME=/opt/maca}、\texttt{LD\_LIBRARY\_PATH=/opt/maca/lib:/opt/maca/lib64}，并设 \texttt{VLLM\_PLUGINS=fl}。

启动：天数在官方命令后加 \texttt{--compilation-config '\{"cudagraph\_mode": "FULL\_DECODE\_ONLY"\}'}；C500 仅使用官方命令，不添加该项。性能评测执行 \texttt{benchmarks/benchmark\_throughput\_serve.py} 并传 \texttt{--test-cases '[[4096,1024,64,256],[16384,1024,64,128]]'}；精度评测执行官网给出的 evalscope 命令，结果见 \texttt{reports/minicpm/math\_500.json} 的 score 字段。

\subsection{复现注意事项}
（1）防止 prefix cache 污染：benchmark 使用 seed=0，同一 serve 上连跑两次相同 input\_len 的负载会产生完全相同的 prompt，第二次会大量命中 prefix cache（本队日志出现过 35.9\% 命中率），使 prefill 近乎免费、总吞吐虚高 30\% 以上。每个数据点都应在新启动的 serve 上获取，A/B 两侧均从冷缓存开始。

（2）C500 需要 $\geq$128 GB CPU 内存：在模力方舟 64 GB 内存规格实例上，纯镜像原版 \texttt{vllm serve} 也会在 inductor 编译阶段被 cgroup OOM killer 杀掉（匿名内存峰值 63.4 GB，被杀时 GPU 显存仅 858 MiB，与显存、负载、代码改动均无关）。128 GB 规格实例全程稳定。

（3）首次启动耗时：C500 需执行 GEMM autotune 预热，实测两台实例分别为 367 秒与 973 秒；第二次启动（triton cache 已存在）约 1–3 分钟。此为正常现象，不是卡死；如确需跳过可设 \texttt{VLLM\_FL\_MM\_WARMUP=0}，但 4k 吞吐约 −6\%、TTFT 变差。

（4）实例间差异：两台 C500 实例的 4k 吞吐相差 4\%、TTFT 相差 66\%，16k 几乎一致。报告因此以区间给数，不以单台最优值充当普遍成绩。
