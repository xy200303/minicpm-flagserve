\begin{abstract}
\setlength{\parindent}{2em}
\raggedright
本研究在 FlagOS 上优化 MiniCPM5-2B 于天数 BI-V150 和沐曦曦云 C500 的推理吞吐。模型、服务参数和评测脚本保持官方设置。C500 优化采样、矩阵乘法（GEMM）布局与 prefill 元数据；BI-V150 重写分页 decode attention，并优化配置查询和门控矩阵乘法。

C500 最终交付提交的 4k/16k 总吞吐为 12465.68/11082.85 tok/s，分别达到官网基线的 2.45/1.58 倍；BI-V150 当前可追溯的镜像对齐测量为 5292.46/4618.41 tok/s，分别达到官网基线的 2.61/5.05 倍，但尚未在最终交付提交上复测。按官方指标取两场景平均，C500 为 11774.27 tok/s，是官网基线的 1.94 倍（图~\ref{fig:headline}）。两平台已测 MATH-500 Level 3 准确率均为 98.1\%；C500 最终复测的平均 TTFT 为 1646.58/18056.74 ms（4k/16k）。

C500 数值测于最终交付提交，并使用关闭启动阶段 GEMM autotune 预热的 \texttt{VLLM\_FL\_MM\_WARMUP=0}。BI 数值测于交付提交的父提交，两者只差换行规范化；最终提交复测仍待可用 BI 实例（\secref{sec:provenance}）。

\noindent\textbf{关键词：}国产芯片；推理吞吐；算子融合；paged decode attention；shape-aware dispatch；vLLM
\end{abstract}

\section{引言}
在硬件、框架和模型固定的条件下，推理吞吐主要受内核效率、访存布局、host 发射和同步开销影响。本报告以 MiniCPM5-2B\cite{minicpm} 为对象，在天数 BI-V150 与沐曦曦云 C500 上，基于官方指定的 FlagOS 软件栈（vllm-plugin-FL\cite{vfl} 与 FlagGems\cite{fg}）开展优化。

两种芯片在指令集、访存层次、运行时和算子库方面存在差异，通用 GPU 上的常用配置不一定适用。例如，Triton 默认的 \texttt{num\_warps=4, num\_stages=3} 在 BI-V150 的 decode attention 上并非合适选择。优化过程先用 profile 和微基准定位瓶颈，再修改内核或执行路径，最后通过官方 benchmark 和 MATH-500 评测端到端效果。后续章节分别介绍 C500 的采样链与 GEMM 路由、BI-V150 的 attention 接入与 decode 内核，以及正确性和复现方法。

\subsection{任务定义}
本赛题要求在不改变模型、不降低精度的前提下，提升 MiniCPM5-2B 在两指定国产芯片上的推理总吞吐（total tokens/s）。优化必须落在框架与算子内部，且需具备实际开发量：KV Cache 与动态批处理、算子融合、内核重写、自研量化策略等均在允许范围内；直接 merge 上游分支、修改 benchmark 脚本、或在缺乏算子优化的情况下切换算子均被禁止。

\section{总体结果}\label{sec:overall}
本章给出交付版本、总吞吐、精度与延迟约束的测量结果。C500 数据来自同一健康实例上的完整复测，并同时保留官网和本机原生基线；各优化项的阶段性收益另用同日交错 A/B 评估，以减少跨时段波动。

C500 启动耗时受 autotune 缓存影响，实测记录跨度约 127–1129 秒，原生基线为 161 秒，不能用单值估计。

\subsection{精度与延迟约束}\label{sec:constraints}

\subsection{GEMM 布局与路由（C500-opt2/C500-opt4/C500-opt6/C500-opt8/C500-opt11）}\label{sec:c500-gemm}
MACA Triton \texttt{mm\_kernel} 的高性能流水主要适配 nn 布局。在 prefill 大 M 的 126 组配置扫描中，其耗时为 vendor mcBLAS 的 1.35–1.67 倍；四种 prefill 形状的 vendor 计算吞吐约为 152–197 TFLOPS。FlagGems 接管 \texttt{aten::mm} 后，原路由无法直接调用 vendor GEMM。为此，prefill 大 M 通过 ctypes 调用 libmcblas 的 \texttt{mcblasGemmEx}（cuBLAS 兼容 ABI），并注册为 custom op 以适配 compiled 区域。默认配置为双布局：小 M（默认阈值 192）或缺少 nn 副本时回退 \texttt{F.linear}，大 M 按路由使用 Triton nn 或 mcBLAS；仅保留 nn\_db 副本的单布局配置可选，但不是默认。另修复 \texttt{vocab\_parallel\_embedding} 在 import 时绑定原版 \texttt{dispatch\_unquantized\_gemm} 导致 lm\_head 未进入优化路由的问题。2026-10-25 复测该形状时，FlagGems Triton 为 667 $\mu$s，直接 mcBLAS 为 430 $\mu$s（1.55$\times$）；同次原生 \texttt{torch.mm} 为 385 $\mu$s，说明 mcBLAS 的收益是相对于 FlagGems 路径，而不是超过所有 vendor 实现。

\subsection{瓶颈分析}

\subsection{自研 paged decode attention 内核（BI-A20）}\label{sec:bi-a20}
BI-A7 之后，decode attention 仍占整步的主要时间。在同一 harness 下逐段测量 stock kernel（B=64/kv=4096/16q-2kv/d=128/block=16/bf16）：loads+QK 耗时 0.54 ms，有效带宽为 509 GB/s；PV 的 \texttt{tl.dot} 耗时 0.36 ms（图~\ref{fig:decode-breakdown}）。loads+QK 虽然耗时更长，但已达到实测 copy 带宽 587 GB/s 的 87\%，接近访存上限，压缩空间有限。PV 则不同：它需要将 p 从 MMA 累加器布局转换为 A 操作数布局，每个 KV block 都产生共享内存往返，这部分开销来自布局转换而不是访存。因此本阶段的优化对象是 PV 的布局转换。

据此重写内核（算子位于 \texttt{FlagGems/fused/paged\_decode\_attention.py}，插件侧为薄封装与派发）：一个 CTA＝1 warp＝一个（seq, kv\_head, 段），使布局转换留在 warp 内；BLOCK\_N=16，p tile 不超过一个 MMA 形状；base-2 在线 softmax，scale 预折 $\log_2(e)$ 走 MUFU；主循环不加 mask，仅 ragged 尾部单独一个带 mask 的 block；段数固定、段长由 device 端 seq\_lens 现算（CUDA-graph 安全），段缓存 slab 在 \texttt{apply()} 即捕获前一次性预分配；段边界按整页对齐，进一步消去逐 token 除模与向量页 gather。混合步中的 decode 行也通过 \texttt{try\_fast\_decode} 进入同一内核。

\subsection{双累加器门控融合与 K 连续权重预打包（BI-A48/BI-A60）}\label{sec:bi-a60}
BI-A48 使用两个独立的 FP32 累加器分别计算 gate/up，共享 A tile 加载，并直接写出 \(gate\cdot\mathrm{sigmoid}(gate)\cdot up\)，避免中间激活的额外读写。官方 4k 两组中位数由 5201.98 增至 5237.32 tok/s（+0.679\%），16k 由 4524.55 增至 4556.53 tok/s（+0.707\%），两种场景的 TTFT 均改善，MATH-500 Level 3 为 98.1\%。

BI-A60 保留上述数值路径，仅改变 B 矩阵的物理布局。设 \(BK=32\)、\(BN=128\)，gate/up 分别重排为 \([K/BK,N/BN,BN,BK]\)，即同一 tile 内的 K 维连续。内核以 \([BK,BN]\) 逻辑形状执行 \texttt{tl.dot}，写回时使用全局 \texttt{rn} 偏移；K、N 可整除时进入该路径，否则回退 A48。预打包结果按权重地址、设备、dtype、形状和 stride 缓存，缓存项保留原权重引用，稳态 decode 不重复转换。图~\ref{fig:a60-layout} 对比了两种布局下一个 B tile 的物理位置：原布局中它分散在 32 个相距 $N$ 个元素的行段里，预打包后是一段连续的 4096 个元素（bf16 下为 8 KB）。

\subsection{复现注意事项}\label{sec:repro-notes}
\begin{enumerate}[label=（\arabic*）,leftmargin=3em]
\item \textbf{检查 prefix cache。}benchmark 使用 seed=0，同一 serve 上重复相同 input\_len 的负载可能命中 prefix cache；本队日志出现过 35.9\% 命中率，并伴随 prefill 开销降低和吞吐虚高。旧日志不能证明各次运行均无命中，因此每个数据点都须检查命中率日志，必要时在新启动的 serve 上测量。各次最终复测的命中率低于 1\%。

\item \textbf{C500 的 CPU 内存。}复现建议采用 $\geq$128 GB CPU 内存（不是官方硬性规格）：64 GB 内存规格实例上，纯镜像原版 \texttt{vllm serve} 也曾在 Inductor 编译阶段被 cgroup OOM killer 杀掉，匿名内存峰值 63.4 GB，被杀时 GPU 显存仅 858 MiB；128 GB 规格实例完成了测试。直接原因是 CPU 内存达到容器限制，不能归因于本队 nn 布局改动；但尚未完成跨版本定位，不能排除 vLLM 或编译器版本对内存峰值的影响。

\item \textbf{启动耗时。}C500 需执行 GEMM autotune 预热。实测记录约 127–1129 秒，原生基线为 161 秒；预热时间随实例和缓存状态变化，不能用固定秒数估计。

\item \textbf{测量波动。}图~\ref{fig:rounds} 给出报告值所依据的逐轮数据。C500 4k 首轮为 11819.77 tok/s，比报告值低 5.2\%，按官方口径剔除；计入均值的后三轮中，C500 的极差为均值的 0.92\%（4k）和 0.07\%（16k），BI 16k 为 0.08\%，BI 第 2、3 次独立 4k 测量为 0.72\% 和 0.78\%。BI 第 1 次 4k 测量是服务启动后的首个场景，后三轮极差达 4.97\%，三轮均值比另两次低约 3\%；原因尚未完全定位，因此保留全部结果并采用三次的中位数，不只展示最佳值。16k 仅完成一次四轮测量，不据此估计跨次波动。
\end{enumerate}

\section{结论}
本工作表明，两款芯片需要不同的优化组合：C500 主要受益于采样融合、GEMM 布局与 prefill 同步消除；BI-V150 则需要同时处理 attention 内核布局、CPU 侧配置访问和门控计算的数据搬运。优化不仅发生在单个内核内部，也发生在权重准备、元数据生成和框架接入边界。

实验得到两点方法上的结论。第一，局部加速不能替代端到端验证：BI-A36 微基准更快却使完整服务回退，因此未采用。第二，收益具有场景依赖性：配置缓存显著改善 4k，但不能据此外推 16k 收益；不同历史阶段的对照也不能相加为最终增益。

当前测量结果及约束判定见表~\ref{tab:throughput}、表~\ref{tab:ttft}。C500 已在最终交付提交上完成复测；BI 已完成官方镜像基线对齐后的父提交测量，但最终交付提交复测仍因评测实例不可用而未能完成。后续首先补齐这一验证，再研究 prefill 分块及更多芯片上的适用性，不以历史结果替代尚未完成的验证。
