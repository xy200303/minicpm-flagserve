# BI-V150 decode 步的全面清点（2026-10-22）

目标：把一步 decode 的每个组成部分都落到实测数字上，确认还有没有未动的空间。

## 一步的账本（4k 用例，B=64，单位 ms）

| 组件 | 每步 | 依据 | 状态 |
|---|---|---|---|
| decode attention（A20，页对齐） | **26.5** | 42 × 0.63 ms/层（隔离实测） | 已优化；地板 22（PV 的累加器→操作数布局转换，见 kernel 文档 §11/§16） |
| 跨段 combine | **2.4** | 42 × 0.057 ms/层 | 该形状地板（融合/分块/warp 三向已否，§15） |
| GEMM（qkv/o/gate_up/down 各 42 次 + lm_head） | **11.3** | 每层 244 µs + lm_head 1059 µs（隔离实测，见下） | 厂商 BLAS，282–505 GB/s（上限 587） |
| 采样（A5 融合）+ metadata + 图重放 | ~1–2 | skip-attention 探针 11.7 ms 减去 GEMM | 已优化 / 已知 −1.5% 量级 |
| **合计** | **≈41** | 与 TPOT 反推的步长一致 | |

## GEMM 的实测底数（M=64，bf16，厂商 BLAS）

| matmul | K | N | µs | GB/s |
|---|---|---|---|---|
| qkv_proj | 2048 | 2560 | 37.2 | 282 |
| o_proj | 2048 | 2048 | 28.2 | 298 |
| gate_up | 2048 | 12288 | 114.7 | 439 |
| down_proj | 6144 | 2048 | 64.1 | 392 |
| lm_head | 2048 | 130560 | 1059.2 | 505 |

每层 244 µs，42 层 10.2 ms + lm_head 1.06 ms = **11.3 ms**，即非 attention 的时间**全部由权重读取解释**，
没有隐藏的额外开销。权重合计 5.3 GB/步 → 有效 450 GB/s（上限 587，已用 77%）。

## 本轮新增的扫描结论

### 1) W8 权重量化 + 厂商 int8 GEMM（唯一还有两位数潜力的项）

- `torch._int_mm`（int8×int8→int32）在这张卡上可用且**更快**：N=6144 时 56.8 → 26.1 µs（2.2x）；
  `ixformer.bnb_qgemm` 是慢/参考路径（6 GB/s、数值不对），不可用。
- 但反量化 epilogue 决定成败：torch 三核版把 qkv/o_proj 拖慢（0.58–0.76x）；
  自写融合 epilogue 在 lm_head 形状 366→110 µs（3.3x, 455 GB/s），小形状还需调 tile。
- 若 epilogue 调到 ~10–15 µs：每层 244 → ~127 µs，整步 GEMM 11.3 → ~6 ms，
  **潜在 +13%**。
- **后续实测（见 `docs/experiments/w8-probe/README.md`，A22）**：把 per-call 激活量化与反量化都算进去后，
  单层 gate_up 是 **120.9 → 157.5 µs（0.77x）** —— 两个额外小核约 80 µs，与 gate_up 的 bf16 GEMM
  同量级，收益被吃光。要藏掉这笔开销只能自写融合 int8 GEMM，而本卡 Triton matmul 比厂商 BLAS 慢约 6 倍。
  **该项已否决**，上表的 +13% 只是"激活已量化"的上界。

### 2) rope + KV 写入融合（小）

vLLM 有现成接口 `do_rope_and_kv_cache_update`（ROCm/AITER 用，Iluvatar 走两次启动）。
融合后每层 2→1 启动，42 层 ≈ 0.07–0.1 ms（0.2%）。

### 3) silu_and_mul 融合（小）

插件里是 torch 链（`F.silu(x1) * x2`，2–3 个启动），42 层 ≈ 0.15–0.2 ms（0.4%）。

### 4) 设备端 metadata（已量过）

A13：去掉每步一次 D2H = −1.5%（说明这条线总量在此量级）。

## 已排除（有测量）
